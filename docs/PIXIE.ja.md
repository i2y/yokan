# pixie

Rust を経由してコンパイルされ、GPU エンジン（gpui）で描画される、GUI 第一の汎用プログラミング言語です。
リアクティブなクラスと宣言的な view を書くと、pixie は借用検査を必ず通る形の Rust を生成します。
つまり、生成されたプログラムはすべて Rust コンパイラという第二の検証器を通ります。
標準ライブラリは、薄い `.rpi` 型バインディングを介した Rust の crate エコシステムです。

```ruby
store Session {
  state name : String = ""
  state saved : Bool = false

  fn update(t: String) {
    name = t
  }

  async fn save {
    await Fs.writeString("/tmp/pixie-hello.txt", name)
    saved = true
  }
}

view Main {
  Column {
    TextField {
      text: Session.name
      placeholder: "your name"
      onTextChanged: Session.update(text)
    }
    Button { text: "save"; onClick: Session.save() }
    if Session.saved {
      Text { text: "saved: #{Session.name}" }
    }
  }
}
```

入力は IME に対応した本物のテキストフィールドに届き、`await` はファイル書き込みをワーカースレッドへ送って UI ループに戻り、store が変われば `if` の行が現れます。
上のコードは全行、今日そのままコンパイルして実行できます（`std::fs::write` に 2 行の `.rpi` バインディング `Fs` を添えます）。

**はじめての方は[言語ツアー](TOUR.ja.md)へ。**
基本文法、型システム、メモリ管理（何が回収され、何が回収されないか）、コンポーネント、アニメーション、アクセシビリティ、パッケージング、二層実行の仕組みまで、図解付きで一周できます。

## クイックスタート

```sh
cargo run -q -p pixie-cli -- install-runtime          # マシンごとに一度
cargo run -q -p pixie-cli -- build examples/counter/counter.pix --run
```

ほかの動詞は `check`、`test`（TAP 出力）、`fmt`、`watch` です。
view 本体を書き換えると、実行中のウィンドウに**プロセス内で約 1 ミリ秒**のホットリロードがかかり、状態はそのまま残ります。
それ以外の書き換えは、約 0.5 秒で再ビルドして起動し直します。
`build --release` は AOT 専用のバイナリを出力します。
ホットリロードの機構とインタプリタは crate グラフごと外れ（counter デモで 60 MB が 13 MB になります）、それでも挙動はバイト単位で同じです。

ビルドしたアプリは、どれもヘッドレスでスクリプトから動かせます。
`PIXIE_SCRIPT="input:Ada,click:save,key:cmd-s,drop:/tmp/x.txt"` は操作を再生してエレメントツリーを出力し、`PIXIE_TIER=interp` は同じスクリプトをホットリロード用のインタプリタで再実行します。
両者の出力はバイト単位で一致しなければならず、これがこのプロジェクトに常設された分岐ゲートです。

## エディタ対応

`extensions/vscode-pixie` は、VS Code に**入力中のエラー表示、hover、定義ジャンプ、補完**を足します。
エラーはコンパイラ自身の診断で、「もしかして」の候補もそのまま出ます。
`.pix` と `.rpi` の色付けもあり、ウィジェットカタログ、エレメントのプロパティ、スタイル、`#{}` 補間、後置の戻り値型、エラーユニオンに、それぞれ専用のスコープを当てます。

まずサーバを 1 度ビルドします。

```sh
cargo build --release -p pixie-lsp
```

次に、拡張を開発モードで入れます。

```sh
ln -sfn "$(pwd)/extensions/vscode-pixie" ~/.vscode/extensions/pixie-language-dev
```

あとはウィンドウをリロードするだけです。
拡張は開いているワークスペースの `target/` からサーバを探すので、チェックアウトして使うなら設定は要りません。
インストール済みのものを使うときは `pixie.lsp.path` を設定してください。
Cursor と VSCodium と Windsurf はそれぞれ自分の拡張ディレクトリを読むので、同じシンボリックリンクがそのまま使えます。
パッケージ化と文法の回帰チェックは、拡張側の README にあります。

`pixie-lsp` は素の stdio サーバなので、LSP クライアントを持つエディタなら何でも使えます。

## 現状

初期段階ですが、実物です。
今日の時点で動くものは次のとおりです。

- **ウィジェット**：cute_ui から移植した全 17 エレメントは Column / Row / Stack / Text / Button / TextField（IME、選択、Tab リング）/ ListView / ScrollView / HScrollView / Image / Svg / DataTable / Modal / BarChart / LineChart / ProgressBar / Spinner で、これに `if` による条件レンダリングと `for` リピータが加わります。
  移植元になかった 18 番目が `Grid` で、均等トラックと、任意の要素に書ける `colSpan:` / `rowSpan:` を持ちます。
  再利用できる**コンポーネント**は view そのもので、既定値付きのパラメータ、インスタンスごとの `state`、`Slot { }` による子要素を持ちます。
  行ごとの状態はリピータの深さを問わず（ネストした `for` の中でも、仮想化リストの中でも）、リピータは求めれば行の位置も束ねます（`for row, i in xs`）。
- **アニメーション**：「この更新をアニメーションさせる」と囲むのではなく、値が動く要素そのものに宣言します（`animate: 200.0` と `easing:`、それに `enter:` / `exit:` のフェード）。
  補間は描画側ではなく要素ツリーの上で走るので、ヘッドレス実行からも見えます。
  `PIXIE_SCRIPT="click:go,advance:100"` は、その瞬間に描かれるはずの 1 フレームをそのまま出力します。
- **アクセシビリティ**：役割と名前と値はカタログ全体で**導出**されるので、ツリーの大半は何も書かずに済みます。
  導出できないもの（見出し、アイコンの代替テキスト、名前付きツールバー）だけを `role:` と `label:` で補います。
  レイアウト用のコンテナは、「グループ、グループ、グループ」と読み上げさせるくらいなら黙ります。
  ツリーは検証の対象になる出力で、`PIXIE_SCRIPT="a11y"` で取り出せます。
  ウィンドウ側も同じ導出の結果を AccessKit に渡します。
- **共通プロパティ**：どのエレメントでも同じ意味を持つプロパティは、ウィジェットごとにフィールドを繰り返すのではなく、書かれたエレメントをコンパイラが包む wrapper として実装します。
  `tooltip:`、`role:` / `label:`、`disabled:`（薄くなり、ウィンドウでもスクリプトでも無効になり、AccessKit にも状態が渡ります）、`width:` / `height:` / `minWidth:` / `maxWidth:`（自前の寸法を持たないエレメント向け）、`theme:`、アニメーションのプロパティ、`colSpan:` / `rowSpan:` があり、どちらの実行でも決まった同じ順序で入れ子になります。
- **スタイルとテーマ**：名前を付けたプロパティ集合です（`style Key { background: "#313244" }`）。
  `+` でマージし、任意のエレメントに `style: Key` で適用し、コンパイル時に完全にインライン化します。
  `pub style` はモジュール間で共有でき、`hover.background:` と `active.background:` はボタンの状態を装飾します。
  色にはセマンティックなテーマトークン（"accent"、"panel"）も書けて、ダークテーマとライトテーマに追従します。
  `theme:` はパレットを部分木に限定するので、暗いウィンドウの中に明るいパネルを置けます。
  値は式なので、アプリは自分のテーマをふつうの状態として持ち、切替ボタンを提供できます。
  その要素に `animate:` を付ければ、テーマの切り替えはクロスフェードになります。
  スタイルの編集も、view 本体と同じく実行中のウィンドウに約 1 ミリ秒でホットリロードされます。
- **本当に遅延する仮想化リスト**：10 万行のリストでも、毎フレーム構築されるのは画面に見えている約 14 行だけです。
- **async と HTTP**：`async fn` と、バインディング呼び出しへの `await` です。
  ブロッキングする処理は gpui のスレッドプールへ回り、実行の意味はウィンドウでもヘッドレスでも一つです。
  組み込みの HTTP クライアントがその上に乗ります（`await Http.get(url)`、`Bytes` を返す `getBytes`、`post`、`Map<String, String>` のヘッダを取る `getWith`）。
- **どこまで進んだかを伝える task**：`async fn load(..) @progress(onProgress)` は、走っている仕事からの報告を受け取るメソッドを指定します。
  `Progress.report(fraction, note)` を呼ぶ場所は、`await` と `await` のあいだの async 本体でも、`await` が仕事を載せたワーカースレッドでもかまいません。
  受け取るハンドラは、World を手にした UI スレッドで走ります。
  報告はすべて届き、最後のひとつは `await` の次の行より先に届きます。
- **自分で走る宣言**：`fn tick @every(1000)` は繰り返し呼ばれるコールバック、`fn save @key("cmd-s")` はショートカット、`fn save @menu("File", "Save")` はアプリケーションのメニューバーの項目で、どれも store ができた時点で結び付きます。
  `fn typed(k: String) @key` はすべてのキーをコードの形で受け取り、`fn opened(p: String) @drop` はウィンドウに落とされたファイルを受け取ります。
  発火する時計も、そこから先の配り方も、ウィンドウのときと同じです。
  だから `PIXIE_SCRIPT="advance:1000"`、`PIXIE_SCRIPT="key:cmd-s"`、`PIXIE_SCRIPT="menu:Save"` は、一秒の経過とひと押しとメニュー選択が届く先へ、そのまま届きます。
- **ホットリロード**：実行中のバイナリが自分の view 本体を読み直し、生きている World に対して組み立て直します。
  `pixie watch` は保存のたびに、プロセス内のリロードで足りるか、完全な再ビルドが要るかを決めます。
- **バインディング**：Rust crate には `.rpi` ファイルを書きます。
  rustdoc JSON から `.rpi` を導出する `rpi-gen` もあります（実物の `std.json` で計測済みで、`std::fs` は 14 関数を束縛し、束縛できないものは理由を付けて飛ばします）。
  `Option<T>` は `T?` としてバインディングを渡り、ユーザー関数も `T?` を受け取り、返し、`nil` を書けます（`when some(v)` と `when nil` で受けます）。
  `Vec<u8>` は COW の `Bytes` 値として渡るので、`std::fs::read` は Int のリストではなくバイト列で返ります。
  C ライクな Rust の `enum` と `struct`、それにタプル struct も渡ります。
  rpi-gen がバリアント単位とフィールド単位の対応を書いた宣言を出力し、フィールドは書き戻す先の Rust の型を名乗れます。
  対応を付けられないもの（ペイロード付きバリアント、非公開フィールド）は、黙って壊れるのではなく、名前の付いたエラーになります。
- **プロジェクトとパッケージ**：`pixie.toml` の `[crates]` テーブルに Rust crate を書くと、pixie が `.rpi` バインディングの表面を自動で導出します（rustdoc JSON から rpi-gen へ渡し、バージョンキー付きのコミットできるキャッシュに残します）。
  バージョン解決は cargo 自身が担当します。
  `[dependencies]` は pixie パッケージを path、git、レジストリインデックス経由のバージョン指定で取り込み、`pixie.lock` がリビジョンを固定します（ロック済みの依存は完全にオフラインで解決できます）。
  パッケージの顔は `src/lib.pix` で、`pub use` で再エクスポートします。
  モジュールはエイリアス（`use foo as F`）、リネーム付きの選択インポート（`use foo.{X as A}`）、ネスト（`use ui.buttons`）に対応し、モジュール間で同じ名前のアイテムも共存できます。
  プロジェクトディレクトリで `pixie build` を実行すると `src/main.pix` をビルドします。
- **書かなくてよいメモリ管理**：オブジェクトは自動参照カウント（ARC）で、値は COW です。
  手で解放するものはなく、裏でヒープを走査するものもなく、借用検査も表に出てきません。
  メソッドが作ってどこにも渡さなかったオブジェクトは、スコープの終わりで回収されます（外に出ないことをコンパイル時に証明します）。
  store や別のオブジェクトが**保持している**ものは、最後の参照が消えたその場で、持っていたものごと解放されます。
  あとでまとめて回収するのではないので、停止時間はありません。
  例外は閉路で、これは `weak` で断ち切れます。
  値（`String`、`List`、`Map`、`Bytes`、`struct`）は COW なので、そもそもオブジェクトストアに入りません。
- **オブジェクトがオブジェクトを指す**：class 型のフィールドは参照を持つので、2 つの持ち主が同じ 1 つのオブジェクトを指し、どちらから書き換えても、もう一方から見えます。
  値の入れ子も自由で、木も再帰も書けます。
- **速度**：値の処理は同じ Rust にコンパイルされ、同じ速度で走ります（実測では、算術ループ 1 反復あたり 0.19 ns、手書きの Rust は 0.13 ns で、どちらもサブナノ秒です）。
  オブジェクトのプロパティの読み書きは約 3 ns で、素の struct のフィールドのおよそ 3.5 倍です。
  これが、ダングリングしない参照と、変化に気付くリアクティブループの値段です。
  ベンチマークはツリーに入っています。
- **trait**：振る舞いを 1 度宣言し、好きなだけ多くの型に実装し、そのすべてを受け取る関数を 1 つ書けます。
  `class` と `struct` が同じ trait を実装でき、呼び出しごとに専用の版が生成されるので、この抽象化に実行時のコストはありません。
- **値レイヤ**：ジェネリクスがひととおり揃います。
  trait 境界付きの関数とメソッド、ジェネリックな struct（`Pair(1, 2)` は推論されます）、`init` コンストラクタを持つジェネリックなクラス（`Basket<String>()`）があり、どれも本物の Rust ジェネリクスへコンパイルされて rustc が単相化します。
  ほかに、リテラルを書ける `Map<K, V>`、`List<T>`、`Bytes`、`nil` を持つ `T?`、`try` と `case` で扱うエラー enum、複合代入演算子の一式があります。
- **エンジン**：Zed のツリーにある gpui を、固定したリビジョンで使います。
  macOS の入力メソッドコールバックにパニック封じ込めのパッチを当てた `gpui_macos` を vendor しています。

ツールチェインは `rust-toolchain.toml` で自分を固定します。
約 500 のワークスペーステストと、31 のデモを通す二層ゲートが緑です。
ゲートは 58 本のスクリプトを二つの実行の両方で再生し、1 バイトでも差があれば失敗します。
アクセシビリティツリーも、アニメーション途中のフレームも、生存しているオブジェクトの数も、その対象です。
ここに挙げた機能は、それぞれ動くデモが `examples/` にあります。
